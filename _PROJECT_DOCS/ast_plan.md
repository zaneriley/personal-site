This document outlines the plan for implementing a runtime transformation system that converts a Markdown Abstract Syntax Tree (AST) into HEEx code on the fly. The approach focuses on dynamically generating HEEx templates from the content AST during application runtime, then caching the generated output. This ensures that end-user performance is comparable to SSR (Server-Side Rendered) HTML, while also supporting hot reload and fluid developer experience.

## Overview

The motivation behind this runtime approach is to:
- Consolidate content rendering into a single, maintainable pipeline executed at runtime.
- Achieve SSR-like end-user performance through effective caching of transformed output.
- Maintain a responsive development workflow with hot reload capabilities, since changes are dynamically recompiled without a full production build.
- Simplify the system by eliminating the need to precompute HEEx code at compile time, thereby supporting dynamic expressions and locale-specific content naturally.

## Architecture and Workflow

1. **Content Flow**
   - Markdown content is parsed into an AST using our existing pipeline.
   - At runtime, a transformation function (or macro) traverses the AST and converts each node into corresponding HEEx code.
   - The generated HEEx fragments are then injected into the respective LiveView templates (such as `case_study_live/show.html.heex` and `case_study_live/index.html.heex`).
   - A caching mechanism stores the output to minimize repeated transformations for unchanged content.
   
2. **Dynamic vs. Static Content**
   - **Static Content**: The static structure (e.g., paragraphs, headings, component placements) is transformed into HEEx code and cached.
   - **Dynamic Content**: Items that require runtime context (such as locale-specific translations) remain as live expressions, ensuring they are up to date.

3. **Error Handling**
   - Runtime transformation errors are caught and handled gracefully, either by logging the error or by falling back to default behaviors.
   - This approach avoids halting the build and supports hot reloading, making it ideal for development.

4. **Incremental Caching**
   - A caching mechanism ensures that once content is transformed into HEEx, subsequent requests for the same content retrieve the cached version.
   - Only modified content triggers re-transformation, which keeps runtime overhead minimal and delivers high performance akin to SSR.

## Dedicated AST Renderer Component Approach

In keeping with our goals of maintainability, idiomatic Phoenix/Elixir practices, and avoiding the need to explicitly declare component names beyond what is defined in the SST, we will adopt a dedicated AST renderer component. Key aspects of this approach include:

- **Single Entry Point for AST Rendering:**  
  The renderer will be a self-contained LiveView function component (e.g., `<.ast_renderer>`). It accepts an AST (produced by our parser and pipeline) and optional layout assigns.

- **Recursive Traversal Using HEEx Syntax:**  
  This component recursively traverses the AST. For each node:
  - It pattern matches on the node type (for example, `:typography` or standard HTML nodes).
  - It uses inline HEEx tags to construct the output, ensuring LiveView can efficiently track changes and minimize HTML diffs.
  - For a typography node, the renderer invokes the predefined `<.typography>` component without needing to hardcode component names elsewhere.

- **Dynamic Layout Handling:**  
  The renderer accepts layout-related assigns (generated by the transformation pipeline) so that:
  - It can wrap the output in layout-specific containers.
  - Different layouts can be applied seamlessly (e.g., different wrappers for case studies versus notes), based solely on the metadata passed along with the AST.

- **Error Handling and Caching:**  
  Consistent with our overall architecture, any errors during the rendering process will be handled gracefully. Additionally, the caching mechanism ensures that unchanged AST content does not incur repeated computational cost.

This approach encapsulates the transformation logic while keeping the integration with LiveView and layout decisions clear and maintainable.

## Key Decisions and Implications

- **Template Insertion**: The generated HEEx code is injected into templates such as `show.html.heex` and `index.html.heex` at designated rendering points.
- **Error Policy**: Unlike the compile-time approach, the runtime system will handle transformation errors dynamically without halting the entire build, ensuring continued hot reload and development efficiency.
- **Performance and Caching**: With a robust incremental caching strategy, the runtime transformation achieves SSR-level performance while allowing dynamic updates and hot reload.
- **Unified AST Structure**: The system assumes a clean, unified AST without the need for legacy HTML fallbacks, simplifying the transformation process.

## Developer Guidelines

- **Transformation Implementation**: The runtime transformation function must:
  - Traverse the AST and generate HEEx fragments for each node type.
  - Distinguish between static and dynamic elements, leaving dynamic parts as live expressions.
  - Handle errors gracefully, logging issues without disrupting the development workflow.

- **Testing and Verification**: In line with TDD principles:
  - Write comprehensive tests to confirm that the generated HEEx output matches expected results for sample AST inputs.
  - Integration tests must verify that LiveView pages render correctly with the dynamically injected HEEx code and that hot reload functions as expected.

- **Caching Strategy**: Ensure that the caching mechanism is efficient and only re-transforms content that has changed.

## Conclusion

This runtime transformation system offers a flexible and performant method for converting Markdown AST into HEEx code. It achieves SSR-like performance through effective caching while preserving a dynamic and responsive development experience with hot reload capabilities. By handling errors gracefully at runtime, the system aligns with both developer needs and end-user performance requirements.
